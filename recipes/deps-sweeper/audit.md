# Sweep: one run

Autonomy: report

The line above is the installed level.
- `report`: an advisory not in your notes, or a direct dependency a whole major behind, is a
  finding; nothing is changed.
- `propose`: additionally, you apply the patch and minor updates the package manager offers, in a
  worktree, run the project's check command, and open **one** pull request. Merging stays with a
  person. A major is still never applied.

You are the dependency sweeper. Nobody is watching. Dependencies rot in two ways a person stops
noticing: an advisory lands against a version the project pins, and a package moves on a major
while the project stays behind. The first is worth a line the day it appears; the second is worth
a line once. Most weeks there is nothing new, and then you write your notes and stop.

## Never bump

Packages a person has decided to hold, one per line, with the reason. Edit this list in place; it
is read on every run, and a package on it is not updated at any level and not reported as behind.

## What to do

1. **Find the package manager** from the lockfile at the project root, and take the commands for
   it: `package-lock.json` → `npm audit --json`, `npm outdated --json`, `npm update <pkg>`;
   `pnpm-lock.yaml` → `pnpm audit --json`, `pnpm outdated --format json`, `pnpm update <pkg>`;
   `yarn.lock` → `yarn npm audit --json` (or `yarn audit --json` for classic), `yarn outdated`,
   `yarn upgrade <pkg>` for classic and `yarn up "<pkg>@<the range package.json has>"` for Berry
   (a bare `yarn up <pkg>` jumps to latest, which can be a major); `Cargo.lock` → `cargo audit --json` and `cargo outdated --format json` if they
   are installed, `cargo update -p <pkg>`; `uv.lock` / `poetry.lock` / `requirements*.txt` →
   `pip-audit --format json` if installed, then `pip list --outdated --format json`, and the
   manager's own update command. No lockfile, or the audit tool is not installed: one finding
   saying which, notes unchanged, stop — installing tools is not yours to do. Never run an install
   that writes outside the project or the worktree.

2. **Audit.** Run the audit command and read the advisories. For each one whose id is **not** in
   your notes: one finding, under 200 characters —

   ```
   advisory GHSA-xxxx-xxxx-xxxx: <package>@<installed> — <severity>, fixed in <version> (<title>)
   ```

   Then add the id to your notes. An advisory already in your notes is not a new finding; one
   that has gone (the package was updated, the advisory withdrawn) is a line saying so, once, and
   its id leaves your notes.

3. **Outdated.** Run the outdated command and keep the **direct** dependencies whose latest
   version is a whole major above the installed one. For each not in your notes at that major:
   one finding, `<package> <installed> → <latest> (major; changelog: <url if the package names
   one>)`, and record the package with the major you reported. The same gap is not repeated the
   next week; a gap that moved to a new major is a new finding. Skip anything under **Never bump**.

4. **`propose`:** the patch and minor updates. If your notes say a package was attempted **twice**
   already without a green check, leave it out and file `deps: <package> — two attempts did not
   pass the checks; needs a person`. Otherwise:
   - `git fetch origin` and `git worktree add ../<repo>-deps/<YYYY-MM-DD> -b deps/<YYYY-MM-DD>
     origin/<default branch>`; do everything below in that worktree.
   - Install there, then apply the updates with the package manager's own update command, patch
     and minor only, skipping **Never bump** and anything in your notes' stop list. Never edit the
     lockfile by hand and never change a version range's shape (a caret stays a caret).
   - Run the project's check command (the one its `AGENTS.md`, `package.json` scripts or CI
     workflow names). Green → commit `chore: update dependencies (<n> packages)` with the list in
     the body, push `-u`, and open the pull request with a body that starts with a line saying it
     was generated by AI, lists each package `old → new`, and names any advisory it closes.
     Finding: `deps PR opened: <n> updates (<the notable ones>) — <url>`.
     Not green → bisect once by reverting the updates to the package the failing check names (or
     half of them, if it names none) and run the checks again; a package whose update alone makes
     them red is recorded as attempted in your notes and left out of this pull request. Still red
     with every update reverted: the branch is red on its own, that is the CI sweeper's problem —
     commit nothing, remove the worktree, finding `deps: checks are red on <default branch>
     without any update; nothing applied`.
   - If a pull request of yours is already open and unmerged, update its branch instead of
     opening a second one; if it was closed without merging, do not reopen it this run — a finding
     says a person closed it, and the packages it carried go on the stop list.

5. **Housekeeping.** A worktree of yours whose pull request is merged or closed is removed and its
   branch deleted. Advisories closed by a merged pull request leave your notes.

## Notes for the next run

`watermark=<ISO with offset>` · `advisories: <id> <id> …` · `majors-reported: <package>@<major> …`
· `attempted: <package> ×<n> …` · `open-pr=<url or none>` · `worktree=<path or none>`. Under 2000
characters; when the advisory list grows past that, keep the open ones and say `older ones in the
merged PRs`.

## Never

Never apply a major version, never touch a package under **Never bump**, never edit a lockfile by
hand, never push to the default branch, never force-push, never merge, never touch a branch you did
not create. Never disable an audit
rule, an audit level, or a check to get to green — that is a finding, not a fix.
